<objective>
Wire `DefaultIntegrationOrchestrator` to be the single invoke pipeline that applies mapping and transform in the correct order relative to auth signing, for the unified proxy API. This closes MAP-06 (body finalized before HMAC) and PIPE-01 (full orchestration resolve -> mapRequest -> auth -> HTTP -> evaluate -> mapResponse). This is the lead vertical slice; the legacy route (03-03) and streaming (03-04) build on this same wiring, and audit/correlation (03-02) runs in parallel.

Purpose: Phase 1 (auth) and Phase 2 (mapping/transform) shipped all collaborators as beans but left them unwired (Phase 2 D-26). Composing them in the strict order D-01/D-02 demand is the core of this phase — the risk surface is ordering/wiring, not algorithms.
Output: A wired orchestrator, a `ResolvedMappingCache` with publish invalidation, the global `mapping-enabled` toggle, and green ordering/passthrough/response-mirror tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller (via upstream gateway) -> unified invoke API | Inbound request body crosses into the pipeline; it is mapped/transformed before being signed and sent to the vendor. |
| api-connector -> third-party vendor (outbound HTTP) | The signed, mapped+transformed body leaves the trust zone; signature must match the body actually sent. |
| published config -> runtime registry | ResolvedMapping cache holds resolved specs; stale entries after publish would apply wrong mappings. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering / Spoofing | `DefaultIntegrationOrchestrator.invoke` (auth signing) | mitigate | MAP-06/D-01: compute `outboundBody = transform.applyRequest(mapRequest(...))` BEFORE `authenticate(...)` and pass it as `requestBody`; `InvokeIntegrationTest.hmacSignsMappedRequestBody` asserts HMAC over the mapped body via WireMock `withRequestBody(matchingJsonPath("$.b"))`. |
| T-03-02 | Information Disclosure | DEBUG stage-timing logs (D-23) | mitigate | Log stage name + millis only; never log request/response bodies, credentials, or SM4 plaintext/keyRef. SLF4J `LoggerFactory`, not Lombok. |
| T-03-06 | Information Disclosure | request-side pipeline failure -> caller | mitigate | D-19/D-20: throw typed `MappingException`/`AuthException`; reuse `RuntimeApiExceptionHandler` -> structured `{code,message,details}` (no stack traces); 5xx for server-side config errors, `vendorHttpStatus=0`. |
| T-03-07 | Tampering / DoS | Groovy mapping/transform execution inside `MappingEngineImpl`/`TransformPipeline` | accept | Scripts are compiled + contract-validated at publish (`ConnectorPublishListener`); Phase 3 only executes already-validated compiled scripts. Sandboxing is v2 (AUTH-V2-02), out of scope. |
| T-03-08 | Tampering | Stale `ResolvedMapping` cache after publish | mitigate | D-21: `ConnectorPublishListener.onPublishInternal` calls `resolvedMappingCache.evict(code3rd)` beside the token-cache evict, so the next invoke re-resolves. |
</threat_model>
